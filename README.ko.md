# Prosona

> 메타인지 기반 멀티 페르소나 서비스 기획 루프. 한 번 인터뷰하고, 그 다음부터는 AI가 굴린다.

## 무엇인가

기획자의 **판단 원칙**을 한 번 추출해 파일로 고정하고, 그 뒤로는 서비스 기획 루프 — 브리프 → 유저 페르소나 → 사용자 여정 → 레퍼런스 → 화면 설계 → QA — 를 AI가 단계별로 혼자 진행한다. 사람은 **단계 경계 4곳에서만** 승인한다.

## 왜 만들었나

목표는 하나다 — **AI가 기획 루프를 스스로 굴리는 시간을 극대화한다.**

그 시간의 상한을 정하는 건 두 가지다.

- **컨텍스트 열화** — 대화가 길어질수록 앞서 정한 정책을 잊고, 용어가 흔들리고, 이전 화면과 모순되는 플로우가 나온다. 여기서 루프가 끝난다.
- **판단 근거 부재** — 기획자의 취향·제약을 모르니 확인하려고 멈춘다. 멈춤이 곧 자율 구간의 종료다.

Prosona는 앞의 것을 **페이즈별 컨텍스트 격리 + 디스크 상태**로, 뒤의 것을 **페르소나 파일 고정**으로 없앤다.

**일차 지표는 runway** — 사람 개입 없이 품질을 유지한 채 통과한 연속 페이즈 수다. 정지는 비용이고, 남기는 정지는 설계된 게이트뿐이다.

## 루프

```
  00 interview   메타인지 인터뷰 → .prosona/planner-persona.md   (기획자당 1회)
        │
        ▼
  10 frame       브리프 + 유저 페르소나            [GATE 1]
  30 journey     페르소나별 사용자 여정            [GATE 2]
  40 reference   Mobbin 동일 도메인 레퍼런스
  50 screens     화면 설계 (여정 × 레퍼런스)       [GATE 3]
  60 review      가상 유저 페르소나 QA             [GATE 4]
        └─ 불합격 → 50으로 루프백 (최대 2회)
  90 handoff     최종 패키징
```

## 게이트 4개

게이트는 runway를 끊는 **비용**이므로 최소한만 남긴다. 게이트 **사이**에서 AI는 질문하지 않는다 — 모호하면 가정을 명시하고 진행한 뒤 게이트에서 올린다. 각 게이트에서 AI는 산출물 요약과 함께 **자기가 내린 결정 3개와 그 근거**를 제시하고 멈춘다.

| 게이트 | 무엇을 승인하는가 | 왜 남겼는가 |
|---|---|---|
| GATE 1 | 브리프 + 유저 페르소나 | 방향이 틀리면 긴 runway가 곧 큰 낭비 |
| GATE 2 | 사용자 여정 | 되돌리기 비용이 큰 구조 결정 |
| GATE 3 | 화면 설계 | 되돌리기 비용이 큰 구조 결정 |
| GATE 4 | QA 결과 | 검증 없는 자율은 폭주 |

`ultra`는 GATE 2·3을 생략해 runway를 4로 늘린다. **GATE 1과 GATE 4는 어떤 모드에서도 제거되지 않는다** — 이 둘은 runway를 줄이는 비용이 아니라, runway가 잘못된 방향으로 길어지는 것을 막는 장치다.

게이트가 아닌 이유로 멈추면(`BLOCK_CONTEXT`, `BLOCK_STATE`, `BLOCK_INPUT`) 그건 결함이다. 원장에 기록되고 0을 향해 몰아간다.

## 강도 — runway 다이얼

```bash
/prosona lite    # runway 1  — 페르소나가 없고 방향이 불확실할 때만
/prosona full    # runway 1~2 — 새 도메인 첫 진입
/prosona ultra   # runway 4  — 페르소나 고정 후의 기본값 (목표 상태)
```

`ultra`가 목표 상태다. 페르소나를 한 번 만든 뒤에도 `ultra`가 안 돌아간다면 페르소나 파일이 부실하다는 신호다.
